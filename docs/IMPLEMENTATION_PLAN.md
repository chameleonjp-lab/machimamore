### 3.1 論理更新の順序

固定60Hzの1tickは、受理入力の取得、期限済み予約の出撃、AI判断と攻撃状態の更新、移動要求・位置の確定、弾とビームの接触、実損傷と破壊、残機予約、終了判定、表示用イベントの順序を明示する。詳細な同時イベントは時刻・攻撃ID・対象トークン／世代で安定した順に処理する。

終了判定は同tickの損傷・破壊を処理した後に1回行い、敗北を勝利より優先する。発射された弾には発射時の操縦担当を保存し、後の操縦交代で命中率所属を変えない。開始・復帰・終了・再出撃で作戦ID／トークン／世代を取り違えない。

### 3.2 検査用の観察

純粋な状態更新は描画・DOMなしで検査できるようにする。実ブラウザの検査はStart、キー、pointer、停止・設定など通常の入力を通す。開始前のfixtureはテスト条件として記録する。開始後のHP・敵・時計・点数の書換えを勝利到達の証拠にしない。

必要なら開発ビルド専用の読取観察口を設けるが、公開ビルドへ状態変更APIや検査用権限を混入させない。単なるURLパラメータで公開版の観察／変更機能を有効化しない。配布物検査で不在を確認する。

## 5 各工程の実装上の要点

### 5.1 起動と移植 P00〜P07

移植ファイルごとに出典path、元commit、元Git blob、適応した理由を `docs/PROVENANCE.md` に記録する。共通飛行など保持する部分は同一条件の入力再生で比較し、作品名・保存キー・兵装数を変えた部分は差分を説明する。旧作の統合simulationやmain.tsをコピーしただけで新作の50機戦に適合したとしない。

台帳は機体トークンと描画プールIDを分け、A/Q/R/Dの移動を専用の遷移関数へ集約する。空き枠の予約は自機→枠番号順で処理し、出撃点検査に失敗してもQから外さない。自機用の予約がある間は別の僚機へ重複した操縦担当を作らない。引き継ぎは既存機の所有を変えるだけで、HP・弾・位置の初期化を呼ばない。

弾は発射成功時にNと弾倉を確定し、弾倉0・装填中・生成失敗の要求を数えない。自機と僚機の装填条件を実際の製品ループで確認する。入力の停止と画面の停止理由を別々に持ち、ダイアログを閉じたイベントが本編を再開させない。

### 5.2 UFOとレーザー P08〜P09

UFOの移動状態と攻撃状態を分離する。警告へ入ると発射地点S・予定点Pを固定し、静止状態を維持する。1バーストの共通照準、発射時刻、残り発射本数、最後のビーム消滅、次に警告可能なtickを明示する。攻撃AIの再評価で毎tick発射予約を作り直さない。

ビームは発射済みオブジェクトとしてUFO本体と別の寿命を持つ。射手破壊後に消し忘れた処理を異常と扱うのではなく、要求された1秒の残存を維持する。作戦結果の確定ではすべて凍結し、既発射レーザーの遅延損傷で結果を書き換えない。

接触判定はビーム線分の太さと動く対象の軌跡を使う。各時間区間の最近接対象だけに線量を積分し、街・地形・機体が奥を遮る。レーザーの見た目だけをraycastして毎フレーム損傷する実装を避ける。高速横切り、接触時刻の境界、遮蔽物の入れ替わり、ゼロ長方向・初期重なりを回帰例にする。

時間積分単体では、静的な同一接触を異なるdt分割で与えた線量を1e-6HP以内で比較する。実ゲームは固定60Hzのため、描画30/60/120Hzでも同じ受理入力列から同じ結果を得る。数値誤差は最初から明記し、失敗後に許容値を広げない。

### 5.3 街とスコア P10〜P11

街の区画IDを損傷・衝突・表示の共通キーにする。複数の建物meshやcolliderは区画へ集約し、1回の事故を50HPより多く繰り返さない。HP0の破壊確定後は区画ごとの破壊イベントを再発行しない。外観の大破・煙火・瓦礫は確定HPから導く。

スコアは生存状態の表示を毎フレーム読み直して加算せず、確定イベント台帳から算出する。破壊数Kは敵D、味方損失P+Wは味方Dに一致させる。実損傷Dと街損失Cは命中前HPで上限を切る。損傷の上限、N/H、破壊・損失の整数性を性質検査で照合する。

結果オブジェクトは終了tickで一度作り、総得点と内訳を保存する。再表示や再出撃ボタン連打、古い音・描画の完了通知は同じ結果を変更しない。検査の期待例は要件書の式から別計算する。

### 5.4 画面と描写 P12〜P15

最初は通常カメラで味方1機・UFO1機・街1区画を含む内部fixtureを使って意味と視認性を確認する。そのfixtureは公開の別モードにせず、製品既定8対8・各50機へ戻して受入検査する。

機体・UFO・母艦・街・海・山並みの識別、警告線と実レーザー、敵/味方マーカー、街の危険方向、残機と出撃数の区別を同じ画面で確認する。装飾・発光・煙が弾道・照準・自機・操作ボタンを隠す場合は、装飾側を調整する。

HUDの現在値と結果の確定値を別にする。進行中の時間点を確定スコアへ混ぜない。N=0は「—（未射撃）」、自機破壊中は復帰／引継ぎ待ちと残秒を明示する。街区画の通知は頻度を制限し、機体数の増加で読み上げ・表示が過密にならないようまとめる。

音は1 AudioContextを共有し、source上限と停止・復帰・再出撃の所有を確認する。レーザーの警告と損傷を別の音にし、初期OFFとON操作を守る。音の信号確認、聴感、実機スピーカー出力を区別する。

### 5.5 バランスと性能 P16〜P19

調整用seed群と確認用seed群を分ける。初期集合は各モードで調整6seed、固定確認6seedとし、勝利率の保証ではなく再現条件の集合として記録する。能動操縦、無操作、単一キー保持、最後の敵放置、連続墜落を同条件で比較し、作戦時間、街損失、味方損失、自機H/N、敵撃破、進行停止を保存する。

試行は1作戦につき能動ゲーム時間600秒を初期の探索上限とする。これはゲームの時間制限ではなく、未終了例を「上限で打切り」と分類するための調査条件。600秒で倒せなかったことだけで不可能とも成功とも断定しない。失敗seedを取り除かず、入力方針の弱さとゲーム側の欠陥を分ける。

必要な数値調整は一度に原因を説明できる要因へ絞る。候補の出撃数・HP・線量・速度・配点を変えた場合はルール版、説明、受入期待値、保存の比較条件も更新する。利用者指定値の変更を含むときは別の判断を必要とする。

性能は初回読込・初回描画・定常・最大負荷・長時間・再出撃を分ける。rAF間隔、CPU更新時間、描画命令、資源数は別の指標で記録する。GPU時間が取れない場合は不明とし、CPUのrenderer呼出し時間をGPU完了時間と呼ばない。

最適化ではinstancing、共有geometry/material、空間索引、pool、画面外の描画省略、装飾密度・解像度を検討する。物理tick・出撃数・画面外AI・弾数・レーザー寿命を端末性能で変えない。変更前後は同じseed・入力列・画質条件を揃え、得点・命中・乱数・終端tickも比較する。

## 7 実行ゲートとCI

### 7.1 検査の実行単位

- G0 基盤: P01で依存取得、最小unit、型/build、1画面起動
- G1 状態: P04で保存則・復帰・終端・停止・再出撃の関連検査をまとめる
- G2 戦闘: P11で射撃・UFO・レーザー・街・スコアを通した結合検査
- G3 通常プレイ: P12でStartから結果・再出撃までの縦切り。P16までに両モードの合法入力経路を追加
- G4 画面と負荷: P17〜P19で複数ブラウザ、レイアウト、画像確認、負荷・資源・実機範囲
- G5 提出候補: P20で最終候補の全必要検査と配布物・通信・権利をまとめる
- G6 リモート: P21でその候補headのGitHub CIとローカル記録を照合する

小さな原因修正は関連する検査を先に実行し、全体検査は工程境界と最終候補でまとめる。直近の実行から短時間しか経っていないという理由だけで全体検査を省かない。複数の修正差分、依存、判定、入力、結果確定、環境変化、既知失敗の有無を見て再実行範囲を決める。

### 7.2 コマンドとworkflowの初期方針

移植元と同じ `npm ci --ignore-scripts`、`npm test`、`npm run build`、`npm run test:browser` を基本とし、実在するpackage.jsonへ定義した後に実行する。必要に応じて文書参照・配布物検査を専用scriptへ分ける。空のscriptや常に成功する代替コマンドでCIを通さない。

CIはPR検査と公開を分ける。PRでは固定Node/lockfile、単体、型/build、Playwright Chromium/WebKit、配布物検査を実行する。新しいworkflowは必要な読取権限を基本とし、テストに公開・本番DB・新しい資格情報を要求しない。配備workflowを準備しても、PR作成やpushでは公開しない。

ブラウザ検査は必要な画面寸法を対象ごとに配分し、同じ無関係な全件を全寸法で重複実行しない。入力所有、長い結果、設定プレビュー、横画面、文字拡大など壊れやすい条件には明示的に組合せを残す。

ネットワーク検査では許可外の通信を記録してfailとする。単にabortしたため送信されなかったことを、送信機能が存在しない証拠にしない。外部ランキングをmockで成功させる経路も新設しない。

### 7.3 CI失敗時

1. 失敗した完全head、workflow/run/job、初回失敗ログを保存する
2. 製品不具合、仕様との不一致、試験の誤り、環境不足、再現性問題を切り分ける
3. 可能な最小再現と同じ故障を検知する回帰例を作る
4. 原因に合う最小修正を行い、関連検査と必要な全体ゲートを再実行する
5. 作業ブランチへ通常pushし、新headのCIを再取得する

同じrunの再試行だけで最初の失敗を解消扱いにしない。テスト削除・skip・期待値追認・許容値緩和・無関係な権限変更で緑にしない。仕様自体を変更する場合は要件IDと根拠を明記し、その新仕様に沿って検査を変える。必要な追加権限や外部判断がある場合はその範囲だけを保留し、無関係な作業を続ける。

終了条件は「最新候補headに必要なCIが終端成功、未解決failなし、ローカルとリモートの対象一致」。pending・running・未実行・workflowなしを成功に数えない。最終候補に修正が入ったら、そのheadについて再度確認する。

## 8 証拠と最終成果物

`docs/VERIFICATION.md` は検査ID、要件ID、対象commit/tree、依存版、環境、seed、入力方法、期待値、観測結果、証拠path、結果区分を持つ。重い生ログ・画像は限定した検査artifactへ置き、長期に必要な要約と固定識別をリポジトリへ残す。期限付きartifactを恒久的バックアップと呼ばない。

結果区分はpass／fail／not_run／blocked／not_applicable。後ろ3つは理由を持たせ、成功件数へ加えない。画像は保存と目視を分け、音は再生可能性と聴感を分ける。模擬端末と実機、PR headと仮マージcommit、配布artifactと公開応答を区別する。

ローカル試験後にcommitした場合は、試験対象のファイルハッシュ／treeと提出先の内容一致を確認して証拠を結ぶ。commit文字列だけを後から書き換えて古いpassを新しいheadのpassにしない。最終diffに試験後の影響する変更があれば再実行する。

最終PRの提出物は以下とする。

- 実装コード・固定依存・テスト・CI
- 要件書と実装計画の最新版、および初期設計からの変更理由
- 元作の固定commitとファイル別の来歴、第三者NOTICE
- 機能・描画・入力・保存・性能の検査結果、失敗修正履歴、実機未確認の範囲
- 実在する試遊／配布物があれば対象版と場所。未公開のURLを公開済みとして記載しない
- 本人採用後の公開手順と、ランキングが含まれない確認

最終PRを再取得し、base/head、Draft、差分、CIを確認する。未マージで提出を終える。初期文書PRの成功とゲーム実装の成功を混ぜない。

## 9 本人採用後の公開ゲート P22

公開準備は静的ビルドの相対パス、distの許可一覧、NOTICE、秘密・開発用hook・不要文書の除外、成果物のハッシュmanifestを検査する。公開先と範囲は本作に限定する。公開の許可があっても代理マージ・main直接pushを行わない。

利用者が採用してmainへ反映した後に、検査済み候補とのtree差分、対象mainの完全SHA、固定依存でのビルド、配備artifactを確認する。未検査差分があれば該当ゲートを再実行する。配備時は指定したSHAと実際のref一致を強制し、古い確認を別のmainへ使い回さない。

実URLでHTML/JS/CSS/NOTICEの内容・形式・版を照合する。下位パス、クエリ、初回相当とキャッシュあり、開始・停止・設定・再出撃を検査する。WebGLや実機が使えない場合は公開応答・DOM確認の範囲だけ報告し、実飛行が成功したとは言わない。ランキング送信や本番記録を作る確認は行わない。

復旧が必要になった場合は、取得できる既知正常artifactと保存形式の互換性を確認し、必要な許可の範囲で行う。公開確認のために他作品の保存・キャッシュ・配備を消さない。
